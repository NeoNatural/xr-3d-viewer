# XR media viewer architecture notes

This is now a standalone native Android/OpenXR photo and video viewer. The runtime home screen has local and SMB media browsers; GameStream host discovery, pairing, app launching, stream activities/services, stream settings, and the native Moonlight transport library are no longer registered or packaged. The older sections below are retained as implementation history.

Unity 6.3 is supported for separate Quest Unity projects, but `com.unity.pipeline` is a Unity Editor package. Do not install it into this Gradle repository or migrate the Moonlight XR renderer to Unity to gain agent access. For this project, the agent build loop is Gradle + ADB + source inspection.

## Build and deployment

- Gradle wrapper: 9.7.1; Android Gradle Plugin: 9.4.0.
- `app/build.gradle` requests Android NDK `29.0.14206865`, compile SDK 37, and target SDK 36.
- Initialize submodules with `git submodule update --init --recursive`.
- The actual debug variant is `./gradlew assembleNonRootDebug` (the plan's `assembleDebug` is outdated for this repository). The APK is under `app/build/outputs/apk/nonRoot/debug/`.
- On this machine, `ndk-build` fails when the checkout path contains spaces. `tools/build-local.sh` syncs source to a no-space temporary path, runs Gradle there, and copies the debug APK back to `build/agent-apks/`.
- Install with `adb install -r <apk>` after connecting an authorized Quest 3 in developer mode.
- Native desktop tests: `make -C app/src/test/cpp test`; Java unit tests: `./gradlew testNonRootDebugUnitTest`.
- Existing `.github/workflows/build.yml` already runs Java and native tests, builds debug and release APKs, and runs lint. Use this as the agent CI pipeline; no Unity Pipeline package is needed.

## Frame and thread ownership

1. `MediaCodecDecoderRenderer.java` creates `XrRenderer` and passes its `getInputSurface()` to MediaCodec. This is the decoder output boundary to reuse for another video source.
2. `XrRenderer.java` starts the **Video - XR Renderer** thread. After native EGL/OpenXR initialization, that thread creates a `SurfaceTexture` attached to the native external OES texture, then wraps it in the decoder input `Surface`.
3. The renderer thread owns `SurfaceTexture.updateTexImage()`, the GL context, the OpenXR frame loop, and `nativeEndFrame()`. `onFrameAvailable()` only signals a pending frame; it does not consume the texture.
4. For model depth, `XrRenderer.java` starts a separate **Video - XR Depth** thread. It binds a shared EGL context and runs `MidasDepthSource.java` via the `DepthSource` interface. Capture and inference are asynchronous to the XR frame loop.
5. `xr_session.c` owns OpenXR session setup and `xrWaitFrame`/`xrBeginFrame`. `xr_layers.c` composes the layers and calls `xrEndFrame`. `xr_gl.c` owns GL resources, edge aware depth upsample, offset search, stereo warp, and GPU timing. `xr_depth.c` stages model input/output; `xr_depthmap.c` filters the depth map.
6. `xr_renderer.h` documents the triple buffered depth textures and separate EGL context. Preserve the synchronization and texture lifetime rules before adding a new source.

## Next integration seam

For local video, feed Media3's decoder into the `Surface` exposed by `XrRenderer`; first verify the decoder lifecycle does not assume a Moonlight stream. For a static image, inspect the OES sampling and capture path in `xr_gl.c`/`xr_depth.c` before choosing a 2D texture or common FBO path. Do not upload textures from the Android UI thread.

Images enter the same external OES texture, depth capture, depth inference, and stereo warp as decoded video. Only the debug manifest exports this activity for direct ADB launch.

## SMB image increment

`SmbBrowserActivity` is a small flat Quest panel for host/share/domain/user/password entry and directory navigation. It performs all SMB calls on one network executor. `SmbStorage` uses NOVA's `jcifs-ng:v2.1.10-multicredit3` and exposes directory metadata, sequential image streams, and a random access file handle for later video work. `SmbClientManager` keeps the authenticated context in process memory while browser and XR image activity hand off the selected URI; credentials are never appended to an SMB URI or persisted. Selecting JPEG, PNG, or WebP opens the existing immersive image activity, which decodes directly from SMB and fits the image on the XR screen. NAS connection and SMB image viewing still need a real server test.

After adding the SMB browser, `testNonRootDebugUnitTest` and `assembleNonRootDebug` passed. The first installed APK crashed at `PcView.initializeViews()` because `layout-land/activity_pc_view.xml` lacked both new buttons; a short lived process check falsely indicated a successful launch. Both landscape buttons are now present. The fixed APK built and installed, and its `PcView` process remained alive after the crash window. Directory entries are closed even when metadata reading fails, and a failed Back navigation preserves the previous directory in the history stack. The user subsequently opened NAS images on the headset, confirming the basic SMB image path; the agent has no NAS address or credentials for automated timing tests.

The user later confirmed the app opens and reported five SMB image issues: missing thumbnails, delayed image display, delayed stereo effect, insufficient maximum strength, and repeated NAS entry. `SmbThumbnailAdapter` now loads visible image rows on two background workers with a 12 MiB memory cache. Successful SMB connections are saved as multiple targets; passwords are encrypted with an Android Keystore AES-GCM key, and the target list fills the connection fields on selection. `StaticImageXrActivity` decodes the image in parallel with XR startup and logs click-to-first-frame timing. The native 3D panel's separation range is now 0–3% of frame width, retaining the original 0.5% default. Static images use the same MiDaS model through a CPU interpreter for faster first depth; Moonlight video still uses the GPU delegate.

On Quest 3 with local `figure.jpg`, the parallel startup posted the first frame in about 0.26–0.29 seconds. GPU depth model creation took about 4.2 seconds after first frame; the still-image CPU path loaded and warmed the model about 0.47 seconds after first frame. First depth publication could not be timed while the headset was idle. The APK with these changes passed `testNonRootDebugUnitTest` and `assembleNonRootDebug`, installed successfully, and `SmbBrowserActivity` started with a live process and no fresh app crash. Thumbnail rendering, saved-target reconnection, SMB image latency, and stronger stereo comfort still require a worn-headset test against the user's NAS.

## Directory and XR image navigation

The user confirmed thumbnails and saved NAS targets work. `SmbStorage` now sorts directory entries by modification time descending, with a filename tie break. The browser collapses the connection form after connecting, leaving a compact Change NAS control. It remembers the last successfully displayed image name in app-private preferences for each SMB directory URI. On returning to that directory, Open last image resolves the saved name against the current listing, so insertions and deletions do not shift the target.

The browser hands an immutable snapshot of the current directory's images to `StaticImageXrActivity`. Two buttons drawn at the bottom of the XR image accept the existing controller screen pointer and trigger press callbacks. A neighboring image decodes on a worker while the current frame remains visible, then replaces the bitmap in the same XR renderer session. This avoids restarting OpenXR and the depth interpreter for every image. The debug APK passed Java tests including newest-first sorting and filename lookup after list changes, built, and installed on Quest 3. An OS reprojected dialog blocked automated app launch during the final device check; in-headset XR button hit testing and NAS navigation still need user verification.

## Static image render resolution

The initial image source created a fixed 1280×720 `SurfaceTexture` and drew each bitmap through a same-sized Canvas. The native OpenXR stereo swapchain was consequently 2560×720 (1280×720 per eye), even when the decoded image had many more pixels. The static image path now uses 2048×1152, producing a 4096×1152 stereo swapchain in model stereo mode. This is 2.56 times as many source pixels. The decoded bitmap's longest side is now smoothly scaled to at most 3072 while keeping more than the 2048 source pixels available for the XR canvas. The MiDaS input remains 256×256, so this increases visible RGB detail and warp output resolution without increasing the model's depth detail. Quest logs confirmed a 2048×1152 Canvas and roughly 0.5 seconds from local activity start to first frame; NAS transfer time still needs a worn-headset test.

## Static image navigation and depth preparation

The XR navigation controls are a separate OpenXR quad immediately above the image. Their ray endpoint must be projected onto that quad's own pose; projecting a navigation hit back onto the image plane visibly deflects the ray. The still-image activity decodes the selected image and four following images while OpenXR starts. A background CPU MiDaS interpreter calculates depth for each prepared image and the renderer uploads the selected prepared map on its depth GL thread. After the third forward image has been consumed, the next four are queued. The previous image stays cached for quick back navigation. Static image cuts reset the native range and per-pixel temporal filters, so the next map is seeded directly instead of fading in from the previous image's depth. Moonlight video retains its temporal filters.

The shipped MiDaS graph has a fixed batch-one reshape. Quest testing showed batch-four tensor allocation fails under XNNPACK and again without XNNPACK (`num_input_elements != num_output_elements`). The image preparation window is four, but model inference currently runs four sequential CPU jobs, publishing each result as soon as it is ready instead of waiting for all four SMB reads. A true batch-four model requires re-exporting the source graph. Visible SMB thumbnails retain up to 48 MiB of original compressed image bytes in process memory; XR image open reuses those bytes when the item's size and modification time match. The cache is cleared when the SMB target changes.

## Baseline verification status

### Depth Anything V2 evaluation

`DEPTH_MODEL_BENCHMARK.md` records the 2026-09-19 same-image MiDaS/V2 previews, a user-supplied MMD clip sample, and Quest 3 ONNX CPU/NNAPI/XNNPACK, LiteRT GPU, and ncnn Vulkan measurements. The debug-only `DepthV2BenchmarkActivity` remains available for isolated measurements; its test weights are pushed to app external files. Quest CPU inference at 392×392 takes about 1.2 seconds; NNAPI provides no material gain with the dynamic ONNX export, and XNNPACK fails to initialize its Resize node. Qualcomm's fixed 518×518 TFLite export runs on the Quest LiteRT GPU delegate at about 181 ms/inference after a 4.6–4.7-second session creation; 60 consecutive runs showed no short-term slowdown. A real MMD frame's GPU output correlated 0.9996 with the ONNX V2 output. Concurrent OpenXR frame timing and in-headset stereo quality still need testing.

The 518×518 Qualcomm V2 Small LiteRT export is now bundled for **still images only**. `SmbBrowserActivity` starts GPU delegate compilation on a process-wide single depth worker while the user browses. `StaticImageXrActivity` prepares both 518×518 RGB input for V2 and 256×256 RGB input for the existing native upload/fallback. Four neighboring images are still prepared sequentially on that worker. The V2 518×518 depth output is bilinearly reduced to the renderer's existing 256×256 texture size. If the GPU interpreter fails, the worker opens the former MiDaS CPU still-image model. Moonlight video still uses its previous MiDaS GPU path.

`testNonRootDebugUnitTest` and `assembleNonRootDebug` passed; the 197 MiB debug APK was installed on Quest 3. The local image probe logged a 4.7 s V2 cold initialization, 187 ms first inference, and successful prepared-depth publication. In a cold browser-then-image run, V2 initialized during browsing (4.5 s); the image's first frame was posted in 264 ms and V2 inference took 275 ms under XR startup load, followed by a successful depth publication. The process stayed alive. This verifies the integration path but not stereo quality or XR frame stability while the headset is worn; those need user viewing and sustained measurements.

The first V2 integration incorrectly required both decode and depth completion before an XR navigation took effect. At the four-image refill boundary, that made the displayed image appear frozen behind the serial GPU queue and allowed a press received during the wait to execute immediately afterward. Navigation now switches as soon as the RGB decode Future completes, publishes V2 depth later, and clears stale presses after the transition. An initial 150 ms recovery interval between speculative inferences was later removed after sustained navigation showed it halved queue throughput. The corrected APK passed unit tests and assembled and installed successfully; worn-headset verification across more than four images remains required.

The next iteration raises the initial forward window from four to eight decoded/prepared images, then adds four when the remaining forward reserve falls to about five. It keeps only two images behind the browsing direction and eight ahead, releases each 518 RGB staging buffer after inference, and logs Java heap and total process PSS after every four completed maps. The XR navigation art has separate red pending states for left and right: an adjacent image whose depth is not ready makes its button red. The user confirmed the red state is visible.

A true fixed batch-4 V2 Small model was also exported with LiteRT Torch 0.9.4 and tested on Quest 3. It delegated 735 of 742 nodes to GPU but took 1.20–1.23 seconds for four images and 25.8 seconds to initialize. Four invocations of the current Qualcomm batch-one model take about 0.72 seconds in the isolated benchmark. An onnx2tf batch-4 export was much worse because most of its graph fell back to CPU. The batch-4 model is therefore not shipped; the larger application prefetch window continues using the faster batch-one graph.

After a sustained navigation test, the process reported about 460 MiB PSS: 134 MiB graphics, 83 MiB native heap, and 44 MiB Java heap. System memory remained available, but the reserved contiguous pool was nearly exhausted. The old prefetch path retained up to eight ARGB bitmaps capped only by a 3072-pixel longest side even though the XR input is 2048×1152, kept the paused browser's 12 MiB thumbnail cache and up to 48 MiB of compressed originals, and allocated a fresh 518×518 float output buffer for every inference. Prepared display bitmaps are now fitted to the actual 2048×1152 input bounds, the browser releases thumbnail bitmaps when entering XR, the compressed-byte cache is cleared after the selected image is decoded, and the single depth worker reuses one interpreter output buffer. Cancelled conversions check interruption between stages and recycle their bitmap. The obsolete 150 ms per-image inference pause was removed because it caused the worker to fall behind after roughly ten quick steps. Queue logs now include the retained bitmap bytes. Worn-headset navigation and PSS/CMA measurements are required to quantify the improvement.

A live red-button capture showed another queue bug in both forward and reverse navigation. The depth worker had been idle for about five seconds, then started the adjacent image only after the red button was clicked. The monotonic forward/backward boundary cursors still claimed those indices were covered after tasks had been evicted or cancelled, leaving holes that were never refilled. Every successful navigation now reconciles a fresh eight-image window from the current index in the actual travel direction and always schedules the immediately opposite neighbor. A weak task set prevents duplicate depth jobs without retaining already consumed images. The expensive process-PSS query remains on the four-completion diagnostic rather than running on every navigation.

The next headset trace showed remaining multi-second stalls in RGB preparation rather than depth inference: button input could precede navigation by about three seconds while V2 inference remained around 0.23–0.28 seconds. After the thumbnail byte cache was cleared, `decodeImage` opened every SMB image twice, once for dimensions and once for pixels. SMB images up to 64 MiB are now read once into a transient byte array and both decode passes use that local copy. Preparation time and decoded dimensions are logged per image. Static image sessions also force Ambilight and image-derived room lighting off; the render loop no longer performs their colour sample, smoothing, glow render, or letterbox readback passes. Moonlight video preferences remain unchanged.

The transient byte-array version improved sustained navigation but could still produce one early large allocation/GC event. Uncached SMB input is now streamed once to an app-cache temporary file; bounds and pixel decode reopen that local file, and it is deleted immediately after the display bitmap is made. This keeps the one-network-read behavior without retaining compressed originals on the Java heap. Static images also no longer post the same bitmap to the input Surface every 200 ms. The OES texture retains its last frame, so the activity posts only the initial image and each actual navigation update. This prevents old frames queued by the 5 Hz loop from briefly reappearing after a switch and reduces the idle poll interval to 25 ms for input responsiveness.

## Grab thumbstick adjustment

While a controller holds the screen's move handle, that controller's thumbstick now adjusts the screen placement. Vertical travel changes viewer-to-screen distance (forward is farther, back is nearer), and horizontal travel changes screen width (right grows, left shrinks). The input has a 20% deadzone, runs at 2 metres per second at full travel, and uses the existing 0.2–8 metre distance and 0.8–8 metre width limits. Each distance adjustment rebases the rigid hand attachment so the next grab frame continues from the adjusted pose rather than snapping back. Outside a move grab, the thumbstick retains its previous host-scroll behavior. The screen pose is still persisted once when the grab ends.

## Local video playback increment

`VideoXrActivity` is the first standalone video source. The home screen's **Open Video** button uses Android's document picker, then Media3/ExoPlayer sends hardware-decoded frames directly to `XrRenderer.getInputSurface()`. The frame path stays GPU-only and reuses the existing video depth thread and DIBR renderer; Moonlight's stream decoder is unchanged. A primary controller click toggles play/pause, controller scroll seeks in ten-second steps, and the VR exit control closes playback. Media3 is pinned to 1.8.1 because 1.9 and later require API 23 while the inherited Android application still supports API 21.

`testNonRootDebugUnitTest` and `assembleNonRootDebug` passed. The debug APK installed on Quest 3 and the home activity stayed live. A 2560x960 AVC MP4 on the headset initialized OpenXR, created Qualcomm's asynchronous hardware decoder, and rendered its first frame into the XR surface about 564 ms after activity start. In-headset visual confirmation, playback controls, audio, ordinary non-SBS MP4/MKV coverage, longer-run depth timing, and seek behavior still need a worn-headset test. SMB video remains a later increment and requires a Media3 `DataSource` over `SmbStorage` rather than downloading the complete file.

The first headset review confirmed video, audio, and live stereo depth, but the invisible click-screen and thumbstick controls were not discoverable. Video sessions now show a dedicated OpenXR control strip below the screen with previous item, ten-second back, play/pause, a clickable progress track, ten-second forward, and next item controls. Its progress and play icon update from ExoPlayer at four Hz. Screen clicks, controller scrolling, and keyboard shortcuts no longer control playback. Video sessions also force Ambilight and image-derived room lighting off. The strip reuses the proven still-image navigation plane, pointer, hit testing, and haptics while retaining distinct art and commands. The local document picker permits multiple selection and passes those URIs to one Media3 playlist; decoder size changes update the physical XR screen aspect between items. Java tests, 104 native checks, the complete debug build, installation, and a Quest hardware-decoder smoke run passed; the expanded strip's appearance and hit targets still require an in-headset user check.

Local video still uses `MidasDepthSource` with the existing 256x256 MiDaS model on the asynchronous video depth thread. The bundled Depth Anything V2 Small path remains still-image-only: at roughly 181–280 ms per frame on Quest 3 it cannot supply live per-frame video depth. No temporal Video Depth Anything model is integrated yet.

## SMB video streaming increment

The SMB browser now recognizes MP4, MKV, WebM, M4V, and MOV files. Selecting one passes the current directory's ordered video list and selected index into `VideoXrActivity`, so the same previous/next controls work for NAS media. `SmbDataSource` adapts Media3 range requests to a dedicated `SmbStorage.openRandomAccess()` handle; seeks call `readAt()` and no complete video download is performed. Media3 still sends hardware-decoded frames directly to the XR input `Surface`. Each playback source closes only its random-access file handle, while `SmbClientManager` retains the authenticated share context for returning to the browser.

The first user test exposed two playlist/throughput issues. Android's single-document grant contained only one local URI, so the local entry now requests a folder grant, lists its supported videos, asks which item to start, and passes the complete alphabetically ordered playlist plus selected index. SMB video was also accidentally disabling the NOVA fork's large read support, defeating its 1 MiB SMB2/3 multi-credit optimization. Large reads are enabled again, sequential seeks no longer reset an already-correct file position, `SmbDataSource` reads ahead 1 MiB, and SMB playback uses a 30–90 second Media3 buffer with 8/12-second initial/rebuffer thresholds. Slow reads over one second and aggregate SMB throughput are logged for follow-up diagnosis.

A live 4K60 stall trace measured jcifs at only 7.9 MiB/s and showed playback buffering at 13.3 seconds while depth inference remained healthy at roughly 26–29 ms and process PSS was about 682 MiB. That rules out depth/GPU and memory exhaustion for this stall. The trace also showed 456 MiB fetched during the short session, so fixed 1 MiB prefetch was changed to 128 KiB for random/probe reads and grows to 1 MiB only after sequential access is established. More importantly, video random access now uses a vendored LGPL-2.1 `libsmb2` 7.0.0 JNI backend; jcifs remains responsible for browsing/images and is retained as an automatic video fallback when native SMB2/3 connection setup fails. The native library is packaged for all four application ABIs.

The first installed libsmb2 build fell back to jcifs for percent-encoded SMB filenames. Its time-prioritized 30–90 second Media3 buffer then exhausted Quest's 256 MiB Java heap on a high-bitrate video; the captured `Transport0` crash was an `OutOfMemoryError` while jcifs was disconnecting. The native adapter now decodes percent-encoded share and path components, reports its exact failing connection stage, and disconnects only a successfully connected context. SMB playback now has a strict 48 MiB target with 10–30 second bounds and 3/5-second start/rebuffer thresholds, with byte limits taking priority. The corrected APK built, passed Java tests and all 104 native checks, and installed on Quest 3; a real NAS playback must confirm the `Native libsmb2 video source opened` log and sustained 4K60 behavior.

Official Video Depth Anything was re-evaluated before attempting integration. The Apache-2.0 Small checkpoint is a 116 MB PyTorch file with 28.4M parameters. The supported offline graph consumes 32 frames at 518x518 and the authors report 6.8 GB of FP16 GPU memory on an A100. Their experimental streaming path still requires the PyTorch DINOv2/temporal-attention implementation and cached hidden states; the project publishes no Android, LiteRT, or ONNX runtime model, and its open ONNX export issue reports that dynamic input export does not work. This cannot safely fit or execute inside the Quest process as currently released. The APK therefore continues to label and use its existing MiDaS video source; it does not misrepresent framewise MiDaS or the still-image V2 graph as Video Depth Anything.
